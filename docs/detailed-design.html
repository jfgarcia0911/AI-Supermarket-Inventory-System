1. Overview

What the system is

  • It works alongside your existing till (EPOS). It is not a point-of-sale system. The till keeps ringing up sales. Sales come into this system once a day as a CSV file exported from the till (a direct connection to the till may come later).
  • This system is in charge of purchases and deliveries, supplier costs, stock quantities, counts, waste, expiry and — because the till comparison has been removed — selling prices.
  • The core of the design is a stock ledger. Every change to stock is saved as a separate record, like transactions on a bank statement. The stock you have is the running balance. This keeps the numbers accurate and explainable: you can always see why a number is what it is.
  • Manual first, AI later. The manual workflows (typing in a delivery, counting, adjusting) are built first. Later, AI invoice reading fills in the same "receive delivery" screen, and a person confirms before stock changes. If the AI gets something wrong, nothing breaks.
Estimated stock = last count + received − sold ± adjustments.
Each part needs its own data source. If one is missing, the number drifts. That is why the daily sales import is part of the first release.

Till comparison removed

The till product-list import, the "missing from till" report and the epos_catalogue_items table have been removed. This also drops "identify products missing from our till system" from the original requirements. Knock-on effects:

  • Selling prices now live in this system. They are entered on each product, or in bulk from a spreadsheet. When a price changes on the till, it must be changed here too, or margin figures (Release 2) will be wrong.
  • Bulk product loading stays, as a general spreadsheet import. It accepts any Excel or CSV file, including one exported from the till. It is a one-way setup tool, not a comparison.
  • The sales import still flags unknown barcodes. That is not a till comparison: it stops sales from quietly disappearing from the stock figures.

Supermarket details that shape the design

  • Cases vs. single items. You buy a case of 24 and sell one can at a time, so each supplier product needs a pack size.
  • Several barcodes per product: the single-item barcode, the case barcode, and old and new packaging.
  • Supplier codes don't match yours. Each supplier has its own code and name for the same product.
  • Weighed and loose items are sold by kg. In-store price labels (barcodes starting with 2) contain the price or weight inside the barcode.
  • VAT. Margins are worked out before VAT. Most food is 0% VAT, but soft drinks, confectionery and alcohol are 20%.
  • Delivery vs. invoice. Deliveries can be short, damaged, substituted or followed by credit notes.
  • Expiry quantities are estimates, because till sales don't say which batch was sold.

How accounts work (built in Phase 1)

  • Owners create every account in Settings > Users: name, email and role. Public sign-up is switched off, and there are no email invitations.
  • Each new account gets a temporary password, shown once to the owner, who passes it on in person or by phone. The first time the person signs in, they must choose their own password before they can do anything else (profiles.must_change_password).
  • Passwords need at least 10 characters, with letters and numbers.
  • Owners can reset a password (the person gets a new temporary one and chooses their own again) and switch an account off. Switching off also blocks signing in straight away; everything the person did stays in the history. Accounts are never deleted.
  • Owners cannot change their own role or switch themselves off, and there must always be at least one active owner, so nobody can lock the shop out.
  • "Forgot password" emails work, but Supabase's built-in email only reaches addresses that belong to the Supabase organisation. Until a proper email service is connected (planned with the Release 2 email reports), staff who forget their password ask the owner to reset it.

Additions

  • Zod. One set of validation rules, used on both the forms and the server.
  • Supabase CLI migrations. Database structure changes are saved as versioned files in Git, so the database can always be rebuilt exactly.
  • Supabase's own client with generated TypeScript types, not an ORM like Prisma. An ORM is a library that talks to the database for you. Prisma usually connects as a powerful user that skips the database's security rules; going through Supabase keeps those rules in force.
  • Stock changes run as functions inside the database (for example "post delivery" or "approve count"). Each runs as one transaction with its own permission checks. The app can never write to stock tables directly.
  • PWA (Progressive Web App). Staff can install the website on a phone home screen like an app, with no app store. Built in Phase 4: an app manifest and icons; it works online only, as agreed.
  • Barcode scanning. Bluetooth handheld scanners behave like a keyboard and are the most reliable option. Phone-camera scanning uses a JavaScript library, because built-in browser support isn't reliable on iPhones. Built in Phase 4 with barcode-detector (the zxing barcode engine), whose engine file is served from our own site, not a third-party server.
  • Resend (or similar) for alert and report emails, and scheduled jobs for nightly alerts, reports and the ledger check.
  • Vitest and Playwright for automated tests; Sentry (optional) for error monitoring.

Environments

There are separate development and live databases. Testing never touches real shop data. Development runs on free plans; paid plans are only needed before the in-store pilot.

Development notes

  • Node.js 24 LTS is required. The Supabase library no longer runs on Node 20, so the app, the seed script and the database tests all need Node 24 (see .nvmrc).
  • Demo accounts owner@example.com, manager@example.com, staff@example.com and viewer@example.com exist only in the development database. They are created, together with the fictional sample data, by npm run db:seed-dev; their password is DEMO_PASSWORD in .env.local. They must never be created in the live database.

Rough running costs (check current prices)

  • Supabase Pro: about $25/month, including daily backups. The free tier pauses inactive projects and doesn't give the backups live business data needs.
  • Vercel Pro: about $20/month per team member.
  • Email: the free tier should cover the shop's volume.
  • AI: paid per use (Release 3 onwards).

AI notes

  • Default model: Claude Opus 5.5 ($4 per million tokens in, $20 per million out; tokens are the units the API charges by).
  • Cost per invoice: a typical 1–2 page invoice should cost roughly 5–20 US cents. This will be measured on real invoices.
  • Cheaper models: Sonnet 5.5 or Haiku 5.5 may be accurate enough. The owner decides, after they've been tested on a set of real invoices.
  • Batch API: halves the cost for invoices that don't need instant results, such as emailed invoices processed overnight.
  • AI never changes stock by itself. Every invoice goes through: AI reads it → the system checks it → a person approves it.
  • Invoice and email text is treated as untrusted. An email could contain text trying to give the AI instructions. The AI only extracts data and has no ability to take actions. A monthly spending cap applies.

6. Business rules

Stock accuracy

  1. Stock only changes through movement records. Nobody types over a stock number.
  2. Movements are permanent. Mistakes are fixed with a reversing entry, so the history always explains the current number.
  3. Actions with several steps are all-or-nothing.
  4. Negative stock is allowed but flagged. If it were blocked, a sales import would fail whenever someone forgot to enter a delivery, even though the till already sold the item. A negative number is a useful sign that something was missed.
  5. Quantities are always stored as single items or kg. Receiving one case of 24 adds 24.

Deliveries

  1. Posting deliveries. Staff check in the quantities; a manager posts the delivery with costs. Stock goes up when the delivery is posted, dated at the time the goods arrived (delivered_at). Deliveries left unposted for more than 24 hours raise an alert.
  2. An invoice can only be posted once, and posted invoices are locked. The same invoice number can't be entered twice for one supplier and document type.
  3. Every line must be matched to a product, or marked "non-stock" (such as a delivery charge), before posting. The lines must add up to the invoice total.
  4. If quantity received ≠ quantity invoiced, the system records a supplier discrepancy you can claim a credit for.
  5. Unit cost = case cost ÷ units per case. All costs are stored before VAT. Credit notes are separate records, never edits to the original invoice.

Adjustments and counts

  1. Every adjustment needs a reason. Adjustments over £25 or 20 units need a manager's approval. Adjustments made by managers are approved automatically.
  2. Count timing. Counts happen outside trading hours, and each count has an "as of" moment. Sales arrive the next morning, so the system can't know the expected quantity at the moment staff count. It works this out when a manager reviews the count: expected = the ledger balance as of that moment. Approval is blocked until that day's sales are imported, and the system warns if any deliveries are still unposted.
  3. Full counts. For products nobody counted, the manager chooses: set them to zero, or leave them unchanged.
  4. Products whose difference is over 20 units or £25 are flagged for a recount before approval. Approval writes count corrections (or opening balances, for the opening count).

Prices, costs and margins

  1. Selling prices are maintained in this system, on each product or in bulk by spreadsheet. When a price changes on the till, it must be changed here too.
  2. Margin = (selling price before VAT − unit cost) ÷ selling price before VAT.
  3. Average cost formula: new average = (stock on hand × old average + units received × new unit cost) ÷ (stock on hand + units received). If stock is negative, it is treated as zero in this formula. Stock value uses the average cost.
  4. (Release 2) A price-rise alert fires when a supplier's new unit cost beats their last cost by more than X%. A margin alert fires when a product falls below its category's target margin. Price alerts use the last cost.

Alerts and catalogue

  1. Low stock means on hand ≤ reorder level. There's only one open alert per type, store and product, and it closes itself when the problem is fixed.
  2. (Release 2) Expiry warnings come N days before the date, set per category (for example 2 days for chilled, 30 for ambient).
  3. (Release 2) A slow seller is a product in stock that sold fewer than X units in the last Y days (default 28 days).
  4. Products with history are deactivated, never deleted.
  5. Each barcode belongs to one active product, and its check digit is validated.
  6. Unknown codes in sales files go to an "unmatched" list. They are never silently dropped. When matched later, the movement is dated at the original sale date. The same file or sales period can't be imported twice, and a missing day's sales raises an alert. Sales dated before a product's last stock count are refused, because the count already includes them.

Access and time

  1. Staff never see costs. Every cost is kept in its own table that stock staff cannot read at all, and screens hide the cost columns from them too (see section 7).
  2. Times are stored in a universal format (UTC) and shown in UK time, which avoids bugs when the clocks change. Daily sales are dated at the store's trading_day_end time.
  3. Money is stored as exact decimals, with 4 decimal places for unit costs (for example £0.4167 per can).

7. Database design (Release 1)

How to read the tables

  • Every table also has an id, created_at and created_by (plus updated_at if rows can be edited). These aren't repeated below.
  • → table means "links to a row in that table".
  • qty is an exact decimal with 3 places, so it can hold kg. It's always stored as single items or kg.
  • money is an exact decimal with 4 places, before VAT unless noted.

How alerts work (Phase 4). The system works the alerts out from the state of the shop whenever the dashboard or the Alerts page opens: new problems open an alert, existing ones are updated, and fixed ones close by themselves. Stock staff see the alerts about the shelves (low stock, below zero, unposted deliveries, unknown barcodes); owners, managers and viewers see all of them. A nightly check and the daily alert email come with Release 2.

How staff are kept away from costs

Every cost lives in its own table that stock staff cannot read at all: supplier_cost_history, stock_costs, stock_movement_costs, supplier_invoice_totals and supplier_invoice_line_costs. Quantities stay in the main tables, which staff can read. Screens also hide the cost columns from staff, but the database is what keeps the costs away from them.

Changed in Phase 2. The original plan was "staff views" that left out the cost columns. Separate cost tables do the same job more safely: a new screen or a new column cannot leak a cost by accident, because staff simply have no access to the tables that hold costs. The database tests prove it.

How imports work

  • Four kinds in Release 1 so far: Daily sales (Phase 3: date, item code, quantity sold, and optionally the description and sales value; day/month/year dates and Excel dates are both understood, and the columns chosen are remembered for the next file), Opening stock (Phase 2: barcode or till code, quantity counted and an optional unit cost, plus when the count happened), Products (category, name, brand, size, sold by, VAT, selling price, barcode, case barcode and size, till code, reorder levels) and Supplier price list (the supplier's code and description, our product's barcode or till code, units per case, case cost before VAT, preferred yes/no). If a price list covers several suppliers, rows for the other suppliers are left out.
  • The file is read in the browser (CSV or Excel .xlsx, up to 20,000 rows). Only the cleaned rows are sent to the server.
  • Columns are matched automatically by their headings ("EAN", "PLU", "Selling price" and so on). The user checks and corrects the matches.
  • The preview shows exactly what will happen (new, updated, unchanged) and a plain-English problem for each bad row, such as "Barcode was shortened by Excel" or "Each row needs a barcode or a till code". Nothing is saved yet.
  • Bad rows are skipped only when the user confirms ("Import 250 rows and skip 6"). When the file matches what is already saved, the preview says "Nothing to import".

9. Security, validation and testing

Security

  • Owner-created accounts only (public sign-up is off; no email invitations). Owners add people in Settings > Users with a temporary password, and each person must choose their own the first time they sign in. Passwords need at least 10 characters with letters and numbers. Optional two-factor login for owners and managers later.
  • Switching an account off blocks signing in straight away, as well as all access to data. Owners can reset a forgotten password by issuing a new temporary one. "Forgot password" emails only reach addresses in the Supabase organisation until a proper email service is connected (Release 2).
  • Row Level Security on every table. These are rules inside the database that decide which rows each user can see or change. Even if the app has a bug, the database refuses anything that isn't allowed.
  • Stock tables can only be changed through the database functions in section 7. Staff read cost-free views.
  • Secret keys (database admin key, Anthropic key) live only on the server, never in the browser or in Git.
  • Invoice files are stored privately and shown through short-lived links. Uploads are limited to approved file types (PDF, JPG, PNG, HEIC) and sizes.
  • Audit log of all changes, and posted records are locked.
  • AI output is treated as a suggestion. It's checked against the rules, approved by a person, and AI spending has a monthly cap.
  • Daily backups (Supabase Pro), with a test restore before go-live.
  • Automatic logout after inactivity on shop-floor devices.
  • UK GDPR: personal data is kept to a minimum (staff names and emails, supplier contacts).

Validation happens in three layers

  1. Form: instant feedback for the user (Zod).
  2. Server: the same Zod rules again, because a browser can never be trusted.
  3. Database: required fields, unique barcodes and invoice numbers, quantity can't be zero, links must point to real rows.

Specific checks:

  • Barcode check digits (EAN-13, EAN-8, UPC-A).
  • "You entered 2,400. Did you mean 24 cases?" warnings.
  • Invoice lines must add up to the invoice total. This catches typos and, later, AI errors.
  • Invoice dates can't be in the future.
  • Every spreadsheet import shows a preview with errors for each row before anything is saved.
  • Barcodes that Excel has shortened (for example "5.06E+12") or that have lost a leading zero are spotted and explained.

11. Sample data

Until real shop data is available, the sample-data/ folder holds test data generated by scripts/sample-data/generate.ts:

  • Products across the main supermarket departments, with categories, sizes, VAT codes, selling prices, barcodes, case sizes, till codes for loose items and reorder levels.
  • Suppliers and their product codes, pack sizes and costs.
  • 28 days of daily sales exports, one CSV file per day, including refunds and a few unknown items to exercise the unmatched-lines list.
  • An opening stock-take for the evening before the sales start, and four weeks of deliveries (Phase 3): each supplier delivers on its own days and tops up whatever would otherwise run low before its next delivery, so stock stays realistic as the sales come in.
All brands, suppliers and barcodes are fictional. The sales file layout is a stand-in: the real till's export format is still to be confirmed. The importer matches columns by their headings and remembers the choice, so a different layout needs no code change.
